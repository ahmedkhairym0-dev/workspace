# Zero-quantity items: technical plan and current cycle review

Date: 2026-10-29

Status: Proposed. Source review complete. Implementation requires approval.

Sources: [US-2026-08-0274](US-2026-08-0274.md) and [US-2026-08-0287](US-2026-08-0287.md).

Target app: `fabrica_construction`. No core or other app changes are proposed.

Scope update: BOQ uploads must also separate positive and zero quantities into the two BOQ child tables.

## 1. Scope and dependency

Implement 0274 first. It provides the zero-quantity tables and source references required by 0287.

The required cycle is:

1. Save a draft BOQ. Route uploaded positive rows to `bill_of_quantity` and uploaded zero rows to `items_with_zero_qty`.
2. On BOQ submit, move zero rows when the setting is enabled. Otherwise, block submit and identify those rows.
3. Create a Contract with positive rows in `items` and zero rows in `items_with_zero_qty`.
4. Route uploaded Contract rows to the same tables by quantity.
5. Activate BOQ zero rows through a BOQ Variation Order.
6. Activate related Contract zero rows through a Contract Variation Order after BOQ activation.
7. Cancel a Variation Order by reversing its movement and quantity contribution using saved source references.

Only reviewed source behavior is confirmed below. No site execution, migration, or application changes occurred.

## 3. Reuse boundaries

### BOQ Variation Order

The flow factory is the correct extension point. Keep the existing controller lifecycle and introduce one flow module.

The default submit path treats a row with `boq_child` as an update to an existing main-table row.
It cannot directly process a reference to a separate zero-child DocType.
The new flow must override movement handling instead of entering `_update_boq_child_item()` unchanged.

`AddNewScopeFlow` already adds quantity to matching rows and subtracts that contribution on cancellation.
Reuse that arithmetic pattern, but retain the zero source reference.
Do not reuse its source-link clearing behavior.

Its matching rule compares allocation type and every hierarchy field.
Story 0287 compares Item Code and the selected allocation value.
Use a specific matcher for the new flow rather than changing matching for existing flows.

The controller inherits BOQ validation. Keep the new BOQ submit movement restricted to actual `BOQ` documents.
Otherwise, inherited submit logic could move draft VO rows before activation validation.

### Contract Variation Order

The existing Contract VO uses active Contract row names and before/after logs.
A zero-child source is a different document type and must not masquerade as `construction_contract_item`.

Add focused activation logic under `services/contract_zero_qty_activation.py`.
Keep validation, source resolution, submit movement, and reversal there.
The controller should dispatch to this module only for `Update Zero Qty Items`.

Keep quantity activation separate from rate-change, descope, and retroactive replacement behavior.
The new type allows quantity editing only, so those operations must not run against its zero source.

`services/variation_order_provisional_sum.py:sync_variation_order_boq()` currently accepts only Current BOQ and New Scope.
Do not add the new type to that allowlist without checking its allocation effects.
BOQ activation already supplies the available quantity. Contract activation must consume availability without adding BOQ quantity again.

### Validation and calculations

Use explicit table parameters or row helpers where existing app methods hardcode `items`.
Limit extraction to methods needed by these stories.
Do not temporarily replace `self.items` to run the full Contract lifecycle against zero rows.

Reuse account, tax, rate, allocation, company, project, reference, and mapped-field rules where applicable.
Check inherited tax calculation separately because it normally reads `items`.
Zero quantity must yield zero quantity-based amounts. Fixed tax charges must retain existing semantics without double application.

## 4. Schema and source identity

Add these fields:

| DocType | Field | Definition |
| --- | --- | --- |
| Construction Settings | `move_zero_quantity_items_on_submit` | Check, default unchecked, label `Move Zero Quantity Items on Submit`. |
| BOQ | `items_with_zero_qty` | Table, label `Items With Zero Qty`, new BOQ zero-child DocType. |
| Construction Contract | `items_with_zero_qty` | Table, label `Items With Zero Qty`, new Contract zero-child DocType. |
| BOQ Variation Order | `variation_order_flow_type` | Add `Update Zero Qty Items`. |
| Variation Order | `variation_order_type` | Add `Update Zero Qty Items`. |

Proposed child names: `BOQ Zero Qty Item` and `Construction Contract Zero Qty Item`.
Use separate child DocTypes as required by 0274.
Carry the business fields needed for mapping, validation, calculations, activation, and restoration.
Set their `qty` field read-only with default zero. Reject nonzero values server-side rather than silently resetting them.
Check Frappe mandatory-field behavior for numeric zero before copying the existing `qty` field definition.

Persist these distinct references:

- Original BOQ source identifier, retained when the original `BOQ Child` leaves the main table.
- Zero-child document name, identifying the stored source snapshot.
- Active BOQ destination name, assigned during activation or merge.
- Contract zero-child source name and active Contract destination name.
- Variation Order and Variation Order row responsible for the movement.

Use the existing `boq_child` value as the stable source identifier while a Contract row remains in the zero table.
Resolve that identifier against the BOQ zero table before activation.
After activation, resolve its saved destination to an actual `BOQ Child` for active Contract processing.

When BOQ activation merges into another row, source and destination differ.
A durable source-to-destination record is required after the zero row is removed.
Extend existing VO logs where suitable. Do not rely on Item Code or an in-memory mapping.
Finalize exact reference field names before coding.

The active Contract must reference the resolved active BOQ destination.
Check duplicates after this resolution, because different original sources can merge into one destination.
Retain original lineage in movement logs for cancellation.

## 5. Story 0274 implementation sequence

1. Add the setting, child metadata, parent tables, and source-reference fields.
2. Add focused BOQ zero-row movement and validation in `services/boq_zero_qty.py`.
3. Read the setting in the actual BOQ submit path. Record affected row numbers before moving or reindexing rows.
4. When disabled, reject zero rows without changing either table. Always reject negative quantities.
5. When enabled, copy business values and source identity, remove processed main rows, and refresh totals and resource references.
6. Extend BOQ upload preview and application to split uploaded rows between both BOQ tables before save.
7. Extend BOQ-to-Contract mapping for zero rows. Review pre-create availability checks so they do not hide zero-only BOQs.
8. Add Contract zero-row routing and pair validation in `services/contract_zero_qty.py`.
9. Extend the Contract upload client and server paths. Validate the complete resulting document before accepting the upload.
10. Apply compatible Contract validation and calculation behavior to the zero table on every save.

### BOQ upload routing

Use the existing BOQ upload action for the complete sheet:

| Uploaded quantity | Result |
| --- | --- |
| Greater than zero | Add or update the row in `bill_of_quantity`. |
| Exactly zero | Add or update the row in `items_with_zero_qty`. |
| Negative | Reject the upload and identify the sheet row. |
| Missing or invalid | Reject through existing upload validation. Do not convert missing quantities to zero for routing. |

Extend `BOQUploadPreview` to load both child tables, including when pagination omits them from the browser payload.
Its `merge_rows()` must build the same final table contents that the upload action will save.
Validate both resulting tables before changing the form or saving the BOQ.

Reuse the existing append-or-replace choice across the complete upload:

- Append: retain existing rows in both tables and apply uploaded rows by their existing row identity.
- Replace: replace both item tables with the routed upload and retain the current resource-reset behavior.

Check both tables when deciding whether to show the append-or-replace prompt.
Preserve existing row-key matching through `name`, `item_key`, or `mir` where supported.
Do not match an existing row by Item Code alone.

For a matched draft row whose uploaded quantity changes category, remove the old table entry and route it to the correct table.
Preserve its source identity across that movement. The same uploaded source must not remain in both tables.
Positive quantity goes into the main table before zero-table validation runs. Do not write a positive value into zero storage.
This draft upload behavior does not replace Variation Order activation for submitted BOQs.

New zero rows uploaded directly have no original `BOQ Child` name.
Assign their stable source identifier server-side and carry it through Contract mapping and later activation.
Do not require Contract-style `boq` and `boq_child` columns when creating new BOQ scope through upload.

Reuse the existing field filtering, parent project assignment, allocation validation, link checks, rate rules, and resource calculations.
Extend source-reference lookups in `controllers/boq_upload_references.py` only where the new table requires them.
Keep applicable duplicate and allocation checks consistent across both BOQ tables.

Do not let the shared grid updater append zero rows into `bill_of_quantity` after the split.
Add a BOQ-specific application step using the same routing helper as the server preview.
Keep the shared sheet utility unchanged unless its existing callback interface cannot apply both tables.

The upload split applies before submit. The checkbox still controls submit handling of zero rows entered in the main table.
The unchecked-setting behavior for rows already routed to zero storage needs the explicit decision below.

Validate a Contract zero reference against its owning BOQ and source row.
The same `(boq, boq_child)` must not appear across both Contract item tables.
Apply this rule to mapped documents, uploads, API requests, and imports.

Keep active-only invoice and remaining-quantity selection restricted to active rows.
Review reports and resource joins individually. Include zero rows only where scope visibility requires them.
Do not change every main-table query into a union.

## 6. Story 0287 implementation sequence

### BOQ activation

1. Add the new type to metadata, creation dialogs, mapping, and the flow factory.
2. Map only zero-table sources into the existing VO `bill_of_quantity` table.
3. Allow `qty`, `type_of_allocations`, and the selected allocation field. Enforce these restrictions server-side as well.
4. Before submit, confirm removal of unchanged zero rows from the VO only. Keep their BOQ zero sources unchanged.
5. Reject negative quantities and remaining zero rows at the server submit boundary.
6. Match active rows by Item Code, allocation type, and its selected value.
7. Add the activated quantity to a matching row. Otherwise, create an active BOQ row from the source values.
8. Save movement state, remove each processed zero source, and refresh BOQ totals and resources.

Allocation mapping:

| Type | Field |
| --- | --- |
| Project | `project` |
| Zone | `zone` |
| Building Type | `building_type` |
| Building | `building_number` |
| Floor | `floor` |
| Unit | `unit` |

Retain existing hierarchy validation when a user changes allocation.
Do not make unrelated hierarchy fields editable.

### Contract activation

1. Add the type to metadata and Contract creation dialogs.
2. Resolve the BOQ activation destination before creating the VO. Block creation if a mapped source is still only in BOQ zero storage.
3. Repeat source and availability checks at submit because the BOQ can change while the VO remains a draft.
4. Map Contract zero rows into VO `items`. Allow quantity editing only, including server-side enforcement.
5. Confirm removal of unchanged zero rows from the VO. Keep their Contract zero sources unchanged.
6. Require each submitted quantity to be positive and within BOQ remaining quantity.
7. Aggregate requested quantities by resolved BOQ source before checking availability. Multiple rows must not consume the same balance independently.
8. Match the active Contract row by `(boq, resolved boq_child)`. Add the activation contribution or create the row.
9. Save movement state, remove processed Contract zero sources, and refresh Contract totals and BOQ contracted/remaining counters.

Use existing availability rules for active items and resources where compatible.
Do not use a display-only remaining value captured when the draft was created.

### Confirmation behavior

Reuse the existing asynchronous pre-submit confirmation patterns in both VO forms.
The BOQ form already warns about zero quantities and removes unchanged Current BOQ rows through separate logic.
Give the new type its own branch so zero means discard from this VO, not delete from the source BOQ.

After confirmation, remove only unchanged zero rows, save the draft, and continue through the established submit workflow.
If the user declines, leave the VO and source tables unchanged.
For API or background submission, reject remaining zero rows. The server cannot show an interactive confirmation.

## 7. Cancellation and movement logs

For each activated source, persist its original snapshot, destination name, operation type, and quantity contribution.
Also retain original allocation, resource references, and any Contract reference changes caused by BOQ merging.

For a newly created destination, reverse the contribution and restore the original zero source.
For a merge, subtract only this VO's contribution and restore the original zero source.
Do not overwrite the destination with a whole historical snapshot if later valid changes must remain.

Use existing invoice and dependency checks before reversal.
Do not cancel BOQ activation while an active Contract still consumes the quantity being reversed.
Cancel the dependent Contract activation first.

Contract merge reversal needs special review: restoring a zero source must not recreate a pair already present in active `items`.
Define reference restoration together with the cross-table duplicate rule before implementation.

Keep movement, logs, quantity updates, and document status changes within the existing transaction.
Test failure paths to confirm that no partial movement survives a failed submit or cancel.
Reuse existing queue paths and repeat source checks inside workers.

## 9. Decisions required before implementation

1. Confirm zero-only BOQ and Contract submission. Recommended: permit valid zero storage without requiring a positive main-table row.
2. Confirm additive merge semantics. Recommended: add the activated quantity, consistent with the cancellation requirement to reduce the quantity added.
3. Confirm mixed Contract activation mapping. Recommended: block creation when any mapped zero source lacks an active BOQ destination.
4. Confirm pair identity for resource-based and split Contracts. Existing active rows can distinguish resources and allocations beyond the required BOQ pair.
5. Confirm how Contract zero references follow a BOQ merge and return on cancellation without violating the cross-table duplicate rule.
6. Confirm whether normal Current BOQ VOs may still delete main rows by setting quantity to zero. Preserve existing behavior unless explicitly changed.
7. Confirm allocation handling for existing `Garage` rows. Story 0287 lists six allocation types, while current hierarchy helpers also include `garage`.
8. Confirm unchecked-setting behavior after BOQ upload routes zero rows directly into zero storage. Recommended: keep upload routing independent of the setting and block submit while either table contains zero rows when unchecked. This extends the original main-table-only submit check and prevents upload from bypassing it.

The source-reference design must be agreed before 0274 coding because 0287 depends on it.
