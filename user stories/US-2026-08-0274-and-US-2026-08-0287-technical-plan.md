# Zero-quantity items: technical plan and current cycle review

Date: 2026-10-29

Status: Replanned against the edited stories on 2026-10-29. Implementation requires approval.

Sources: [US-2026-08-0274](US-2026-08-0274.md) and [US-2026-08-0287](US-2026-08-0287.md).

Target app: `fabrica_construction`. No core or other app changes are proposed.

Scope update: BOQ uploads must also separate positive and zero quantities into the two BOQ child tables.

### Requirements from the edited stories

BOQ activation merges only when Item Code, allocation, rate, and accounts match.
Contract activation continues to match by `BOQ` + `BOQ Child`.
Both merge operations add the activated quantity to the existing quantity. They do not replace it.
Cancellation subtracts the exact contribution recorded at submit.

The BOQ developer section still describes Item Code and allocation alone.
This plan follows the more specific edited expected behavior, including rate and accounts.
The account fields need clarification because the reviewed standard `BOQ Child` schema has no Account link fields.

Keep the previously requested BOQ upload split and detailed cancellation cycle in scope.
Story 0274 retains its setting, routing, quantity, and duplicate rules.

## 1. Scope and dependency

Implement 0274 first. It provides the zero-quantity tables and source references required by 0287.

The required cycle is:

1. Save a draft BOQ. Route uploaded positive rows to `bill_of_quantity` and uploaded zero rows to `items_with_zero_qty`.
2. On BOQ submit, move zero rows when the setting is enabled. Otherwise, block submit and identify those rows.
3. Create a Contract with positive rows in `items` and zero rows in `items_with_zero_qty`.
4. Route uploaded Contract rows to the same tables by quantity.
5. Activate BOQ zero rows through a BOQ Variation Order.
6. Activate related Contract zero rows through a Contract Variation Order after BOQ activation.
7. Cancel a Variation Order by reversing its movement and quantity contribution using saved source references.

Only reviewed source behavior is confirmed below. No site execution, migration, or application changes occurred.

## 3. Reuse boundaries

### BOQ Variation Order

The flow factory is the correct extension point. Keep the existing controller lifecycle and introduce one flow module.

The default submit path treats a row with `boq_child` as an update to an existing main-table row.
It cannot directly process a reference to a separate zero-child DocType.
The new flow must override movement handling instead of entering `_update_boq_child_item()` unchanged.

`AddNewScopeFlow` already adds quantity to matching rows and subtracts that contribution on cancellation.
Reuse that arithmetic pattern, but retain the zero source reference.
Do not reuse its source-link clearing behavior.

Its matching rule compares allocation type and every hierarchy field, but does not compare rate or accounts.
The edited story also requires the same rate and accounts, so this matcher is insufficient for the new flow.
Use a specific matcher with Item Code, allocation type, selected allocation value, rate, and the agreed account fields.
Do not change matching for existing flows.

The controller inherits BOQ validation. Keep the new BOQ submit movement restricted to actual `BOQ` documents.
Otherwise, inherited submit logic could move draft VO rows before activation validation.

### Contract Variation Order

The existing Contract VO uses active Contract row names and before/after logs.
A zero-child source is a different document type and must not masquerade as `construction_contract_item`.

Add focused activation logic under `services/contract_zero_qty_activation.py`.
Keep validation, source resolution, submit movement, and reversal there.
The controller should dispatch to this module only for `Update Zero Qty Items`.

Keep quantity activation separate from rate-change, descope, and retroactive replacement behavior.
The new type allows quantity editing only, so those operations must not run against its zero source.

`services/variation_order_provisional_sum.py:sync_variation_order_boq()` currently accepts only Current BOQ and New Scope.
Do not add the new type to that allowlist without checking its allocation effects.
BOQ activation already supplies the available quantity. Contract activation must consume availability without adding BOQ quantity again.

### Validation and calculations

Use explicit table parameters or row helpers where existing app methods hardcode `items`.
Limit extraction to methods needed by these stories.
Do not temporarily replace `self.items` to run the full Contract lifecycle against zero rows.

Reuse account, tax, rate, allocation, company, project, reference, and mapped-field rules where applicable.
Check inherited tax calculation separately because it normally reads `items`.
Zero quantity must yield zero quantity-based amounts. Fixed tax charges must retain existing semantics without double application.

### Contract activation

Do not add rate or accounts to the Contract merge key. The edited Contract rule still uses the BOQ pair.

### Confirmation behavior

If the user declines, leave the VO and source tables unchanged.

## 7. Cancellation and movement logs

Apply this behavior only to `Update Zero Qty Items`.
Cancel the submitted VO through the standard document lifecycle. Do not directly change `docstatus` to draft.
Deleting or abandoning a draft VO must not change BOQ or Contract source tables.

### Movement state captured on submit

Persist one movement entry per processed VO row in the existing BOQ or Contract VO logging structure:

- VO name and row name.
- Parent BOQ or Contract, source DocType, original zero-row name, and original source identifier.
- Complete zero-source business values, including allocation, rate, agreed account fields, and original BOQ references.
- Destination DocType and row name, with operation `Insert` or `Merge`.
- Exact quantity added and the destination quantity before activation.
- Resource identities and source-to-destination reference changes needed for reversal.
- Reversal status, set only after successful cancellation.

Keep source and destination references separate. A merge must not overwrite the saved original source identifier.
Keep original allocation values even if the BOQ VO changes allocation before activation.
Rows discarded from a draft VO after confirmation have no movement entry and need no reversal.

### BOQ Variation Order cancellation

Use the existing `BOQVariationOrder.on_cancel()` dispatch to the new flow.
Implement the inverse movement in `UpdateZeroQtyItemsFlow.apply_cancel()`.
Do not route its logs through the existing main-row update or deletion reversal unchanged.

1. Load the VO's unreversed movement entries and the current BOQ.
2. Resolve destinations by saved row names. Do not search by Item Code or the current allocation.
3. Calculate each destination's quantity after subtracting this VO's recorded contributions.
4. Validate that the remaining quantity supports existing Contract allocations and resource commitments.
5. Block cancellation if dependent Contract activation or later source changes prevent valid reversal. Identify the affected documents.
6. For an inserted destination, remove it only when reversal leaves no quantity or dependent use.
7. For a merged destination, subtract only this VO's contribution. Retain the preexisting row and unrelated valid changes.
8. Restore each processed source to BOQ `items_with_zero_qty` with quantity zero and its original identity, allocation, rate, and accounts.
9. Reverse reference changes recorded by this movement. Keep zero Contract rows linked to the restored original BOQ source.
10. Recalculate BOQ resources, totals, contracted quantities, and remaining quantities through the existing flow refresh.
11. Mark movement entries reversed and retain them for audit.

Aggregate contributions before checking a destination when multiple sources merged into the same main BOQ row.
Restore every original zero source separately.
Remove only resources created solely for a removed destination. Preserve resources belonging to a retained merged row.
Resolve cancellation by the logged destination name even if its rate or accounts changed after activation.
Do not rerun the merge matcher during cancellation.

#### BOQ reversal rules

For each destination, calculate `quantity_after_cancel = current_quantity - sum(recorded_activation_quantities)`.
Use the persisted submit contribution, not the current VO row quantity or a quantity recalculated from rate.
Reject a negative result before changing any row.

| Submit operation | Cancellation action |
| --- | --- |
| Insert, resulting quantity zero | Remove the created main row and its unused resources. Restore every contributing zero source. |
| Insert, resulting quantity positive | Retain the main row if remaining independent contributions and their references are valid. Restore this VO's zero sources only. |
| Merge into a preexisting row | Retain that row and subtract this VO's contribution. Restore the original zero sources separately. |
| Unchanged zero row removed from the draft VO | Perform no reversal. Its source never left zero storage. |

Restored zero rows must keep their original zero-child names and stable source identifiers.
Restore their original business values from submit snapshots, with `qty = 0`.
Do not copy the current active row into zero storage because allocation, rate, or accounts may have changed.
Do not copy active contracted or remaining counters into the restored zero row.
Recalculate applicable counters through the existing BOQ rules.

#### BOQ log and lifecycle integration

Extend `BOQ Variation Order Logs` with the zero-source snapshot and movement references needed by this flow.
Keep its existing active-row snapshot available for destination reversal.
The current `boq_child` log field alone cannot identify both the original zero child and a merged active destination.

Capture resource state before submit movement, including which resources belong to the source and which belong to a preexisting destination.
During cancellation, restore source resource relationships where needed and recalculate retained destination resources from the reduced quantity.
Keep resource references valid when removing a created main row.

Use this execution order inside the existing cancel transaction:

1. Load and validate all movement records, current destinations, and dependent references.
2. Calculate all resulting quantities and check Contract and resource commitments.
3. Apply quantity subtraction, remove eligible created rows, and restore original zero sources in the loaded BOQ.
4. Restore movement-owned reference changes and save the BOQ through the existing submitted-document update path.
5. Run the flow's existing resource and total refresh against the saved row state.
6. Persist the reversal state once the complete operation succeeds.

Keep the existing base flow refresh in one place. Do not also call it from `apply_cancel()` if the base `on_cancel()` already does so.
Verify that recalculated totals persist after refresh. Do not leave corrected values only in memory.
Retain normal BOQ validation and restrict the existing submitted-child update allowance to this controlled lifecycle path.

If a later VO replaced or split a logged destination, use existing dependency rules to require reversal of that dependent change first.
Do not choose a replacement destination through item matching.
If the saved source or destination history cannot support reversal, stop before mutation and identify the affected VO row.

Cancel dependent Contract activation before BOQ activation when the Contract still consumes the quantity being reversed.
A Contract zero row that only references the original source does not consume that quantity.
Preserve that reference when BOQ activation is reversed.

### Contract Variation Order cancellation

Add a type-specific branch in `VariationOrder.before_cancel()` after applicable dependency validation.
Use `services/contract_zero_qty_activation.py` to reverse movement instead of the generic quantity and rate reversal methods.
Retain the inherited `on_cancel()` behavior and comments after the movement succeeds.
Run zero-activation reversal once. Do not also apply provisional-sum snapshot restoration to the same movement.

1. Load the VO's unreversed movement entries and the current Contract.
2. Resolve active destinations and original zero sources from the saved references.
3. Apply existing invoice checks and validate later VO dependencies before changing rows.
4. Aggregate this VO's contributions by destination and calculate the resulting active quantities.
5. Reject reversal that would reduce a destination below its invoiced or otherwise committed quantity.
6. Remove an inserted destination only when its remaining quantity is zero and no dependent use remains.
7. For a merged destination, subtract only the recorded contribution and retain the preexisting quantity and row identity.
8. Restore each processed source to Contract `items_with_zero_qty`, with quantity zero and its original BOQ pair.
9. Validate pair uniqueness across both Contract tables after restoring the original references.
10. Recalculate Contract row values, taxes, totals, and outstanding amounts through the existing compatible refresh methods.
11. Refresh BOQ contracted and remaining quantities to release the reversed Contract quantity.
12. Mark movement entries reversed and retain them for audit.

Contract cancellation releases BOQ availability. It must not undo the separate BOQ activation or reduce BOQ planned quantity.
Do not run generic rate-change replacement or descope restoration against these movement entries.

### Insert and merge examples

| Movement | State after submit | State after cancel |
| --- | --- | --- |
| BOQ insert, activation 5 | New main row has 5. Original zero source is absent. | Remove the unused new main row and restore its original zero source. |
| BOQ merge, baseline 10, activation 5 | Existing main row has 15. Original zero source is absent. | Existing main row returns to 10 and the original zero source returns. |
| Contract insert, activation 4 | New active row has 4 and consumes 4 of BOQ availability. | Remove the unused active row, restore the zero source, and release 4 of availability. |
| Contract merge, baseline 6, activation 4 | Existing active row has 10. Original zero source is absent. | Existing active row returns to 6, restore the zero source, and release 4 of availability. |

Examples assume no later quantity changes or dependencies. For valid independent changes, subtract the contribution from the current quantity.

### Contract pair conflict on reversal

A restored Contract zero row uses its original source pair. The retained active row uses its resolved active BOQ destination.
These pairs can differ when BOQ activation merged the source into another BOQ row.

If restoring the original pair would still duplicate a retained active pair, the requested rules conflict.
Block cancellation before mutation and identify the conflicting row until the pair policy is resolved.
Do not delete the preexisting active row, invent a new source reference, or silently skip source restoration.
The identity decision in section 9 must settle this case before implementation.

### Transaction, queue, and amendment behavior

Validate all reversal entries before applying any movement.
Keep restored rows, quantity updates, reference changes, logs, and cancellation status within the existing transaction.
A failure must leave the VO submitted and both source and destination tables unchanged.
Reuse existing queued cancellation paths and perform dependency checks inside the worker.

After cancellation, an amended VO must revalidate its restored zero sources and current BOQ availability.
It must create new movement entries on submit. It must not reuse the canceled VO's applied movement state.

## 9. Decisions required before implementation

1. Confirm zero-only BOQ and Contract submission. Recommended: permit valid zero storage without requiring a positive main-table row.
2. Confirm the exact BOQ account fields and their source. Additive merge semantics are settled by the edited story for both VO types.
3. Confirm mixed Contract activation mapping. Recommended: block creation when any mapped zero source lacks an active BOQ destination.
4. Confirm pair identity for resource-based and split Contracts. Existing active rows can distinguish resources and allocations beyond the required BOQ pair.
5. Confirm how Contract zero references follow a BOQ merge and return on cancellation without violating the cross-table duplicate rule.
6. Confirm whether normal Current BOQ VOs may still delete main rows by setting quantity to zero. Preserve existing behavior unless explicitly changed.
7. Confirm allocation handling for existing `Garage` rows. Story 0287 lists six allocation types, while current hierarchy helpers also include `garage`.
